## Quick Search popup

Quick Search is enabled by default. The search home page shows the current shortcut. Dismissing this hint keeps it hidden when you reopen the app; the shortcut remains available.

![Quick Search shortcut on the search home page](/images/product-search-home-en.png)

While SAG Wiki is running, press **⌘⇧Space on macOS** or **Ctrl+Shift+Space on Windows** to open Quick Search from another app. You can also choose **Quick Search** from the menu bar or tray. The shortcut remains available after closing the main window and stops when you quit the app.

![Quick Search popup](/images/product-quick-search-en.png)

Typing searches the existing local index and shows up to ten matching files in a scrollable left-hand list. Use **↑ / ↓** to select, **Enter** to open the matching passage in the main window. Clicking a file or moving with the arrow keys updates the highlighted original text on the right. Use **Esc** to dismiss and return to the previous app. Clicking outside also dismisses the popup. Use **⌘ / Ctrl+Enter** or **Full search** to see all results in the main window.

**Deep search** requires a configured Jev service and runs only when you click it. The popup does not automatically generate search summaries. Opening a passage or the full results preserves the search mode used in the popup.

Go to **Settings → Shortcuts → Quick Search** to enable or disable the global shortcut. Click the shortcut field, press a key combination, then choose **Apply shortcut** to save and activate it immediately. You do not need to click the main **Save settings** button. If the shortcut is already in use, an error is shown and the previous shortcut remains available.

## Quick search

Enter words from your documents to search locally. Quick search needs no model key and works well for names, terms and known passages.

![Search results and source highlights](/images/product-search-en.png)

Results are grouped by file. Select a result to read its source on the right. Use the Back button at the top left of the reader to return to the search summary, or open related passages to choose a match within that file. Use match navigation to move through the source. The document actions menu lets you open the document or reveal it in its folder.

Edit the query in the input above and submit it to search again. Use the top-left Back button to clear the query and view recent searches.

The active match emphasizes its entire source paragraph. Markdown uses a dark background with light text in the light theme; HTML outlines the paragraph while preserving the source text and background colors to maintain contrast. Markdown previews use the selected passage's source position, so semantic results remain highlighted even when they do not contain the original search words. Find-in-document still locates the words you enter and uses the corresponding paragraph marker style.

HTML tables in Markdown render as tables in search previews, Quick Search, and citation previews, preserving merged cells and bold formatting. Editing retains the original HTML; table examples explicitly placed in code blocks continue to display their source.

![HTML table with merged headers and formatted values](/images/product-html-table.png)

HTML paragraphs, headings and links also render with their alignment and image dimensions preserved. Local images with relative paths load from the document's folder; PNG, JPEG, GIF, WebP and SVG are supported. External images are not loaded automatically. Editing retains the original HTML, and HTML examples inside code blocks remain source code.

![Local logo, centered heading and links in a README](/images/product-readme-html.png)

## Read search results

- Drag the divider between the results and source text to resize the list. Switching files with the mouse or keyboard automatically scrolls to the currently selected passage highlight.
- Use find-in-document, related passages and focus mode in the reader header to inspect matches.
- Large documents show the target passage first and load the remaining content progressively. In narrow windows, use Back to return to the results.

## Deep search

Configure a Jev endpoint, model and API key, then choose deep search. Describe the information you need as a complete question:

```text
How does this project handle login and permissions?
```

SAG2 retrieves candidate passages, uses Jev to assess evidence relevance, expands the search when needed, and returns relevant sources. This is useful for questions spanning multiple files.

![Semantic results highlight the selected source passage](/images/product-search-semantic-en.png)

## Comparing search modes

| | Quick search | Deep search |
| --- | --- | --- |
| Input | Words, names, known text | Complete questions or semantic descriptions |
| Execution | Local full-text search | Local index and Jev service |
| Configuration | No model key required | Jev configuration required |
| Output | Matching files and text | Evidence relevant to the question |

## Timing

The interface displays elapsed time and processing status. Tool calls in Q&A also include request handling. Compare the question, scope and retrieval settings when comparing timings across views.

## Search settings in detail

Location: **Settings → Search settings**. Read [Technical overview](/en/docs/sag2) for the difference between candidates, expansion and final results.

![Automatic summary and SAG2 retrieval settings](/images/product-search-settings-en.png)

### Automatic search summary

On by default. When a search finds results, Search summary opens and expands automatically, using the question and selected results to generate a short summary. Select a result on the left to read its source, then select Search summary to return. If automatic summaries are disabled or no answer model is configured, the first file opens instead.

![Search summary opens automatically](/images/product-search-summary-en.png)

Configure an [answer model](/en/docs/models) first. Provider charges may apply. Summary time is separate from pure retrieval time.

### Summary source count

Defaults to 10, minimum 1, with no fixed maximum. It limits how many results are considered for the summary. Inputs exceeding the answer context budget are trimmed. More sources increase input volume and do not guarantee a better summary.

### SAG2 parameters

| Setting | Default / range | Effect |
| --- | --- | --- |
| Candidates per round | 50 / 10–100 | New candidate limit per Q&A retrieval round. More candidates broaden scoring and increase Jev work. Desktop deep search uses a fixed 100 instead. |
| Expansion seeds | 10 / 1–20 | How many ranked, not-yet-expanded passages become search starting points. More seeds add context and terms. |
| Expansion term limit | 20 / 1–500 | Caps terms and full-name phrases extracted from seeds. More terms widen retrieval and may add irrelevant candidates. |
| Expansion rounds | 1 / 0–2 | Rounds after initial retrieval. 0 means initial retrieval only; 1 allows up to 2 rounds total; 2 allows up to 3. Stops early without new candidates. |
| Returned passages | 10 / 1–100 | Final passage count for Q&A retrieval tools, separate from per-round candidate count. Desktop deep search shows at most 100 files; CLI `-m` controls its output limit. |
| Target chunk characters | 512 / 400–12000 | Indexing chunk target. Preserves sentences and neighboring context; long sentences may exceed it. Changing this rebuilds indexes. |

### Adjusting parameters

Start with defaults. Keep the question and file scope fixed, change one value at a time, and compare factual source coverage and elapsed time.

- Too much output: reduce returned passages before reducing candidate coverage.
- Missing cross-file facts: inspect expansion rounds and seed count.
- Insufficient passage context: adjust chunk size, then wait for reindexing.
- Slow retrieval: inspect candidate count, expansion rounds and Jev service time.

### Restore default parameters

Restores the six SAG2 values to `50 / 10 / 20 / 1 / 10 / 512`. Save afterward. It does not reset the summary toggle or summary source count. A changed chunk target triggers index updates.

### Rounds and requests

The implementation permits at most three Jev scoring rounds. Final local ranking makes no additional model calls. Large candidate sets are batched under request budgets while retaining whole candidates. A single candidate plus shared evidence exceeding the budget produces an explicit error rather than truncating the source.

Retrieval rounds therefore do not equal Jev HTTP request counts. More candidates, seeds or larger chunks can increase batching and time.

## Local Conan embeddings (core integration)

The Rust core now exposes a local Conan ONNX encoder and a top-50 retrieval helper for fusion. This integration does not add desktop controls. It reads the 1792-dimensional `sentence_embedding` output, packs positive values into 224 bytes, and ranks stored chunk vectors by Hamming distance through sqlite-vec. Chunk embeddings use the existing seven-day cache, keyed by text hash and model path/revision. Encoders share a session per model signature; poisoned sessions are discarded before reuse.

Models are not bundled and discovery never downloads them. The core checks the local Hugging Face cache for `onnx-community/Conan-embedding-v1` (`onnx/model_int8.onnx` or `model_int8.onnx`, plus `tokenizer.json`), then an explicitly imported component. Cache location precedence is `HF_HUB_CACHE`, `HF_HOME/hub`, then `~/.cache/huggingface/hub`. The caller supplies a snapshot revision or a local ref such as `main`. A missing model prints a prompt and returns an empty Conan leg so callers can fuse the remaining available legs. WeMM runtime encoding remains outside this integration.

Explicit component import accepts already downloaded streams and trusted size/SHA-256 values. It stages files, verifies them, and atomically installs an immutable revision. Failed verification leaves existing revisions intact. Discovery also verifies imported components; it does not select or overwrite an active model.

ONNX Runtime is loaded dynamically. Set `ORT_DYLIB_PATH` to the native library file. Otherwise the core searches beside the executable, its `lib` directory, platform library directories from `LD_LIBRARY_PATH` (Linux), `DYLD_LIBRARY_PATH` (macOS), or `PATH` (Windows), then `/usr/local/lib` and `/usr/lib` on Unix. Native libraries come from the [Microsoft ONNX Runtime 1.31.0 release](https://github.com/microsoft/onnxruntime/releases/tag/v1.31.0): Linux x86_64 uses `onnxruntime-linux-x64-1.31.0.tgz`; macOS and Windows require the archive matching their platform and architecture. Linux expects `libonnxruntime.so`, macOS `libonnxruntime.dylib`, and Windows `onnxruntime.dll`. The x86_64 prebuilt runtime requires AVX2; older CPUs can terminate with an illegal instruction. macOS/Windows native loading is **unvalidated (未验证)**.

The six-question comparison against the existing Python bf16 chunk vectors: with the local int8 ONNX artifact, Q1–Q6 top-50 set overlaps are respectively **47, 49, 47, 48, 48, 49 out of 50**; the differences come from int8 quantisation numerics (about 33/1792 bits flipped), not a Rust implementation bug. The acceptance standard is fused top-10 evidence coverage matching the Python leg, with the retrieval score staying at 4.0/5: measured evidence sets match exactly for Q1/Q3/Q4/Q5/Q6, Q2 differs by one boundary chunk but still scores 1.0, for a total of 4.0/5. The regression test asserts this standard.

Before changing model handles, the public compatibility check compares corresponding text/float-vector samples. Dimensions must agree and mean cosine similarity must be at least 0.9. A failed check leaves the current handle in place; it never rewrites stored vectors or automatically re-embeds chunks. Empty samples, zero vectors, and non-finite values are rejected. Packed binary vectors cannot substitute for float samples in this check.

## Fast/accurate retrieval and multi-leg fusion

Retrieval has two tiers (retrieval config `mode`, default fast).

- **Fast**: SAG2 leg only — the existing deep-search behaviour, unchanged.
- **Accurate**: SAG2 and vector legs run in parallel (Conan; when the WeMM model is missing it falls back to the Conan + SAG2 two-leg setup), each contributing top-50, fused with RRF (k=60) plus a per-author top-5 quota, taking the final top-10. Six-question retrieval score: 4.5/5.

**Graceful degradation**: if any leg fails (missing model, vector table not built, ONNX load failure), retrieval falls back to the available legs without interrupting; a missing model never triggers a download.

**Retrieval knobs** (retrieval config): keyword/vector weights default 0.8/0.25, similarity threshold 0.2, candidate pool 50; fusion parameters RRF k=60, per-author quota 5, per-leg top-50, final top-10. Existing libraries automatically migrate the old default 0.7/0.3 to 0.8/0.25 on first open; custom weights are unaffected.

**Literal exact match**: retrieval has an additional literal-match leg that finds buried numbers, names and other exact content, running alongside BM25; its hits join the candidate pool before fusion.

**Folder weights**: each folder can carry a weight (default 1.0) that joins the hybrid score, so higher-weight folder content ranks first on ties.

**Dual-tier parsing**: parsing has fast and accurate tiers. Fast uses lightweight text extraction; accurate adds layout and table recognition (Docling) after extraction, so table content becomes retrievable.

**Incremental sync**: bulk import resumes from a checkpoint, so an interrupted import does not redo finished files; deleting a file removes its chunks from the full-text and vector indexes, so it is no longer retrievable.

**Index parallelism**: Settings → Files → Index parallelism, default 8, range 1–64; takes effect on the next indexing task and does not rebuild existing indexes. Bulk indexing uses a bounded worker pool with a memory-budget backpressure so a large import does not exhaust memory.
